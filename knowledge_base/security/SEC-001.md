## Purpose

IAM misconfiguration is the highest-blast-radius category of finding this
system can surface, and per SHARED-002-2.5 it is also the one category this
system will never fix automatically. This SOP defines Meridian Retail
Technologies' baseline IAM controls — least-privilege policies, root account
protection, access key rotation, console MFA, and timely review of
externally-shared access — and is deliberately written so that every clause
below routes to a human, every time.

## Scope

Applies to every IAM policy, role, user, and group in every AWS account in
scope, including roles created by Terraform under `infra/` and `demo/infra`.
Does not apply to AWS-managed service-linked roles, which are exempt from
SEC-001-1.1's wildcard-policy check by construction (AWS controls their
content).

## Definitions

- **Customer-managed policy**: an IAM policy created by Meridian, as opposed
  to an AWS-managed policy.
- **Wildcard grant**: a policy statement whose `Action` and `Resource` are
  both `"*"` with `Effect: Allow` and no condition narrowing scope.
- **External access**: any resource-based policy or trust policy that
  grants access to a principal outside Meridian's AWS Organization,
  detected by IAM Access Analyzer.

## Policy Clauses

### SEC-001-1.1 — No wildcard customer-managed policies

```clause-meta
controls: [IAM.1]
prowler_checks: [iam_policy_allows_privilege_escalation, iam_customer_attached_policy_admin_privileges]
severity: high
default_action: manual_ticket
iac_managed_action: "terraform_pr:remediate_security"
risk_tier: {non_prod: T3, prod: T3}
references: [SHARED-002-2.5]
```

No customer-managed IAM policy MUST grant `"Action": "*"` combined with
`"Resource": "*"` and `Effect: Allow`, with no narrowing `Condition`. This
applies whether the policy is attached to a role, user, or group, and
regardless of environment — a wildcard grant in `dev` is exactly as
dangerous as one in `prod` because credentials and trust relationships are
frequently broader than the environment tag suggests.

### SEC-001-1.2 — Root account protection

```clause-meta
controls: [IAM.6, IAM.9]
prowler_checks: [iam_root_hardware_mfa_enabled, iam_root_mfa_enabled, iam_avoid_root_usage]
severity: critical
default_action: manual_ticket
iac_managed_action: null
risk_tier: {non_prod: T3, prod: T3}
references: []
```

The root account MUST have MFA enabled at all times; for the production
AWS Organization, the second factor MUST be a hardware security key, not a
virtual/software MFA device. The root account MUST NOT be used for routine
operations — any root-account API call or console sign-in not tied to a
documented account-recovery event is itself a Critical finding.

### SEC-001-1.3 — Access key rotation

```clause-meta
controls: [IAM.3]
prowler_checks: [iam_rotate_access_key_90_days]
severity: medium
default_action: manual_ticket
iac_managed_action: "terraform_pr:remediate_security"
risk_tier: {non_prod: T3, prod: T3}
references: [SHARED-001-1.2]
```

Every IAM user access key MUST be rotated at least every 90 days. A key
older than 90 days is a Medium finding regardless of whether it has recent
usage; an unused key older than 90 days SHOULD instead be deleted, not
rotated (see IAM.2 in Meridian's account-hygiene review, tracked outside
this SOP).

### SEC-001-1.4 — Console MFA

```clause-meta
controls: [IAM.5]
prowler_checks: [iam_user_mfa_enabled_console_access]
severity: high
default_action: manual_ticket
iac_managed_action: "terraform_pr:remediate_security"
risk_tier: {non_prod: T3, prod: T3}
references: []
```

Every IAM user with console access MUST have MFA enabled. This is High, not
Critical, because it requires the attacker to also have the user's password
— but it is still routed to a human, never automated, because disabling a
person's console access as a side effect of a false-positive would be
disruptive out of proportion to the automation's benefit.

### SEC-001-1.5 — External access review SLA

```clause-meta
controls: []
prowler_checks: [accessanalyzer_enabled]
severity: high
default_action: manual_ticket
iac_managed_action: "terraform_pr:remediate_security"
risk_tier: {non_prod: T3, prod: T3}
references: [SHARED-001-1.2]
```

Every active IAM Access Analyzer finding (a resource-based policy or trust
policy granting external access) MUST be reviewed within the High SLA (7
days from `first_seen`): either confirmed as an intentional, documented
cross-account or third-party integration, or remediated. An unreviewed
external-access finding that breaches SLA MUST be escalated per
SHARED-001-1.2.

## Procedures

1. To manually check a policy for a wildcard grant: `aws iam
   get-policy-version --policy-arn <arn> --version-id <v> --query
   "PolicyVersion.Document"` and inspect each statement.
2. To verify root MFA: `aws iam get-account-summary --query
   "SummaryMap.AccountMFAEnabled"` (console) and, for hardware MFA on prod
   organizations, confirm via the Organization's designated break-glass
   runbook (external to this SOP).
3. To list keys older than 90 days: `aws iam list-users --query
   "Users[].UserName"` then `aws iam list-access-keys --user-name <name>
   --query "AccessKeyMetadata[?CreateDate<='<date-90d-ago>']"`.
4. To review an Access Analyzer finding: `aws accessanalyzer
   list-findings --analyzer-arn <arn> --filter
   '{"status":{"eq":["ACTIVE"]}}'`.

## Exceptions

High and Critical findings under this SOP require a compensating control
and, for Critical, CISO approval per SEC-006-6.3 — see SHARED-003. A common
compensating control for SEC-001-1.1 while a wildcard policy is narrowed is
a service control policy (SCP) at the Organization level denying the
highest-risk actions (`iam:*`, `organizations:*`) regardless of the
role's own policy.
